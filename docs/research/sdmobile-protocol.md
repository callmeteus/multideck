# Stream Deck Mobile: protocol decision record

Status: **A, viable**, with a clear implementation route and four unknowns left
to close. This page replaces the earlier placeholder. It records what the shipped
desktop app actually does, not what we assumed.

Analysis date: 2026-11-24. Analyst: MultiDeck maintainers, on the maintainer's own
machine, using the official installer.

## Verdict

The phone does not talk to an opaque cloud tunnel. The desktop app runs its own
**WebSocket server** on the local network, advertises it over **mDNS**, and speaks
**Protobuf** messages in a package called `vsd2`. Authentication is a distinct
message pair (`Authenticate` / `CancelAuthenticate`), not a transport level
certificate. This is a reproducible design, so the adapter is feasible.

Four things still have to be measured before code is written, all listed under
[Open unknowns](#open-unknowns).

## Architecture as observed

```text
phone (Stream Deck Mobile)
  |  mDNS browse _vstreamdeck2._tcp
  v
StreamDeck.exe
  ESDVSD2Server  (WebSocket, dynamic port, observed 28198)
  ESDVSDServer   (legacy VSD v1, two TCP channels: ctrl + data)
  ESDCoraDocksManagerEx (Network Dock, mDNS _elg._tcp)
```

### Service discovery

| Service | Purpose | Evidence |
|---|---|---|
| `_vstreamdeck2._tcp` | VSD2, the current phone/virtual device server | string at 23758880, log `### [VSD2 Server] ... starting Bonjour` |
| `_vstreamdeck._tcp` | VSD1, legacy virtual device server | string at 23752256, `ESDVSDServer` |
| `_elg._tcp` | CORA network dock | string at 23713760, `ESDCoraDocksManagerEx` |

The app logs the chosen port:

```text
### [VSD2 Server] init with workstationID=WE1qigCf1de1Iw5uzt8fhg
### [VSD2 Server] port 28198 is available; starting Bonjour
### [VSD2 Server] resumed
```

`workstationID` is a 20 character base62 identifier, generated by the app. The
port is picked dynamically from a free port at startup, and a secret preference
named `bonjour_disabled` can suppress publishing.

### Transport and handshake

The server is a plain WebSocket (no TLS) that answers a standard upgrade:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
Server: VSD2 Server
Access-Control-Allow-Origin: *
```

Observed from `Get-NetTCPConnection` and a manual upgrade against `ws://[::1]:28198/`.
The server sends nothing until the client sends the first message. A second port,
28196, is the plugin SDK WebSocket, unrelated to the phone.

Because the channel is `ws://`, a LAN capture during pairing would be readable
without a TLS key. This is the cheapest way to close the remaining unknowns.

### Wire probing

A manual upgrade against a live instance (`ws://[::1]:28198/`) plus a few crafted
frames narrowed the framing:

| Frame sent | Server behaviour |
|---|---|
| nothing | no frame, connection stays open |
| empty binary | close frame, code 1008, payload `03 f0` + `error parsing message` |
| text `hello` | connection closed |
| binary `08 01` | connection reset |

So the channel is binary only, and the server validates the first message as a
well-formed `vsd2.*` protobuf message before doing anything else. Sending an
unrelated payload produces a policy violation, not a parse error response, which
is why the envelope and field numbers must come from the descriptor table or a
capture rather than from guessing.

### Framing: resolved

The first probes sent empty or synthetic payloads and the server closed them with
`error parsing message`. That was a red herring: the server expects the first
frame to be a valid `ClientMessage` with a `hello` payload, and an empty
`ClientMessage` is rejected by its state machine before any reply.

The breakthrough came from the Android client, not from guessing. The APK ships
`messages.proto` and `AppSettings.proto`, which contain the full `vsd2` schema
with field numbers, the `ClientMessage`/`ServerMessage` oneof envelopes, the
image formats and the pairing semantics. A manual `HelloFromClient` built from
that schema produced a real `HelloFromServer` with the workstation ID, host name,
version, protocol version 3, the server public key, `clientNeedsAuthentication`
and the service endpoints. Confirmed on 7.6.1:

```text
0a 53 ...            ClientMessage.hello
52 b8 01 ...         ServerMessage.hello (field 10)
  0a 16 WE1qigCf1de1Iw5uzt8fhg
  12 0f DESKTOP-0NJ2SSU
  1a 0b 7.6.1.23033
  20 03               protocolVersion
  2a 20 <server key>  publicKey
  30 01               clientNeedsAuthentication = true
```

So a WebSocket binary frame is exactly one `ClientMessage` or `ServerMessage`
protobuf message. No length prefix, no type byte, no extra envelope.

`Authenticate` carries only a `requestID`; the security model is a user
confirmation of the six hex digits derived from the client public key, not a
signature exchange. That is why the adapter can implement pairing without a
vendor service.

### Authentication

Presence of the following strings, next to `clientNeedsAuthentication` and
`AuthenticationRejected`, means pairing is an application level exchange:

- `Authenticate`, `CancelAuthenticate`, `clientNeedsAuthentication`,
  `AuthenticationRejected`, `Error.Code`, `Error.reason`
- `### [VSD2 Server] sodium_init error`, and a `LibsodiumDRG` string, so libsodium
  provides at least part of the cryptography
- the app reads and writes a Windows credential entry on connect
  (`EGQTCredentialStore::ReadPasswordWithServerAndUserName`, `CredRead() err: 1168`)

The pairing UI text is stored next to the QR template:

```text
Open Stream Deck Mobile (version 2.0 or later) on your iOS or Android device,
select "Add computer", and scan this QR code.
https://streamdeck.elgato.com/c/?t=%1&w=%2
```

The app also bundles the `QR-Code-generator` license, so the QR is produced
locally. The URL carries two parameters: `t`, most likely the pairing token, and
`w`, most likely the workstation identity. Whether the phone calls Elgato's cloud
with `t` or only uses it locally has to be measured; this is the single biggest
remaining risk to a fully local implementation.

### Legacy VSD v1 (still present)

`ESDVSDServer` uses two TCP channels with a small token vocabulary, visible as
`CTRL`, `DATA`, `HELLO`, `PING`, `NOTE`, `WANT` in one packed string. Log lines
name the flow: `incoming ctrl inquire -- creating session`,
`incoming data inquire -- creating data channel`, `remote established session`.
A VSD2 adapter should target `_vstreamdeck2._tcp` first; VSD1 is only interesting
for older app versions.

### CORA (Network Dock)

`_elg._tcp`, `ESDCoraDocksManagerEx`, `ESDCoraPairingDialog`, `cora_seen.json`,
and the log line `try to connect Dock` / `try to connect unit`. This is the
network dock protocol already documented by other open source projects. It is a
different device class from the phone, and it is not required for the mobile
adapter.

## Open unknowns

| Question | Status | Notes |
|---|---|---|
| Protobuf field numbers | Resolved | The Android client ships `messages.proto`; the reconstructed schema lives in `packages/libs/devices/sdmobile/proto/vsd2.proto` |
| WebSocket envelope | Resolved | One binary frame equals one `ClientMessage` / `ServerMessage` |
| `Authenticate` content and secret | Resolved | Only `requestID`; trust is a user confirmation of the BLAKE2b-derived code, then the key is remembered |
| QR parameters `t` and `w`, cloud involvement | Partly | Discovery now works over mDNS `_vstreamdeck2._tcp`; the QR path is not needed for a local host and is unused by MultiDeck |

## Next experiments, in order

1. Test the implemented adapter with the real phone: run the desktop with
   `MULTIDECK_DEVICE=mobile`, open Stream Deck Mobile, add the computer, compare
   the six digit code logged by the host, and confirm that the keys render and
   that presses run actions.
2. Capture one pairing session on a PC hotspot to confirm the auto-trust default
   is acceptable, then replace it with an in-app confirmation dialog.
3. Only then polish: image format selection, keypad sizes, page requests and
   shortcuts.
